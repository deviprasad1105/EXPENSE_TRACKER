# Database guide

The app stores everything in Postgres: locally the **`dev_dr_expense`** database (owned by the `dev_dr_expense` user)
in the `LOCAL_FCHUB_DB` container, port 5445; on Vercel, a hosted Postgres. The backend creates any missing tables on startup
from `backend/app/models.py`, and `backend/sql/schema.sql` holds the same DDL for reference.

All dates and times are stored in the app's timezone (`TIMEZONE` in `.env`, default `Asia/Kolkata`).
Primary keys are `GENERATED BY DEFAULT AS IDENTITY` integers. Booleans are `SMALLINT` (1 = true, 0 = false).

## Overview

```
                    ┌──────────────┐  manager_id (self reference: who you report to)
                    │  APP_USERS   │◄─────────────┐
                    └──────┬───────┘──────────────┘
       ┌──────────┬────────┼───────────┬──────────────┬───────────────┬────────────────────────┬─────────────────┬───────────────┐
       ▼          ▼        ▼           ▼              ▼               ▼                        ▼                 ▼               ▼
  DAILY_ITEMS  EXPENSES  FUNDS   DATA_SHARES    NOTIFICATIONS   USER_AVATARS   USERNAME_CHANGE_REQUESTS   PASSWORD_RESETS  SUBSCRIPTIONS
       │          ▲  │       │   (owner → viewer)
       └──────────┘  │       │   daily_item_id (which template an expense came from)
                     ▼       ▼
                     ACCOUNTS ◄── ACCOUNT_TRANSFERS (from / to)      also per user: BUDGETS, USER_BACKGROUNDS
                     account_id (paid from / received in)
```

Deleting a user deletes all their rows in every table (`ON DELETE CASCADE`). References that only
point *at* a user (a manager, who created an expense, who decided a request) are set to `NULL` instead.

## APP_USERS
Everyone who can log in, plus their role, approval state, reporting line and preferences.

| Column | Type | Meaning |
|---|---|---|
| `id` | INTEGER, PK | User id. Used inside the login token, so it never changes. |
| `username` | VARCHAR2(50), unique | Login name. Letters, digits, `_ . -`. |
| `email` | VARCHAR2(120), unique | Used for reminder emails when SMTP is configured. |
| `full_name` | VARCHAR2(120) | Display name. |
| `password_hash` | VARCHAR2(200) | bcrypt hash. The plain password is never stored. |
| `role` | VARCHAR2(10) | `USER`, `ORG_ADMIN` (admin of one organisation) or `ADMIN` (the app's super user). |
| `status` | VARCHAR2(10) | `PENDING` (just registered, cannot log in), `APPROVED`, or `REJECTED`. |
| `manager_id` | INTEGER, FK → `app_users.id`, nullable | Who this user reports to. Always `NULL` for an `ADMIN`. |
| `org_admin_id` | INTEGER, FK → `app_users.id`, nullable | The `ORG_ADMIN` whose organisation this user belongs to. Not shown to the user. |
| `created_at` | DATE | Registration time. |
| `approved_at` | DATE | When an admin approved the account. |
| `username_changed_at` | DATE, nullable | Last username change, by the user or by an admin. Starts the 15-day lock. |
| `avatar_updated_at` | DATE, nullable | When the profile photo last changed. `NULL` means no photo. |
| `show_tour` | SMALLINT | 1 = show the welcome tour after login. Set to 0 by "Don't show again" or in Settings. |
| `theme` | VARCHAR2(10) | `light` or `dark`. |
| `feature_expense` | SMALLINT | 1 = the user's plan includes expense tracking (default 1). |
| `feature_split` | SMALLINT | 1 = the user's plan includes split bills (default 0). Set by an admin. |
| `feature_subscription` | SMALLINT | 1 = the user's plan includes the subscription tracker (default 0). Set by an admin. Admins always have every feature. |
| `feature_accounting` | SMALLINT | 1 = the user's plan includes accounting (default 0). Needs `feature_expense` too. Set by an admin. |
| `token_version` | INTEGER | Written into every sign-in token. Raised on a password change or reset, "sign out of all devices" and an admin lock, which revokes every older token. |
| `failed_logins` | INTEGER | Wrong passwords in a row. Reset by a successful sign-in. |
| `login_blocked_until` | DATE, nullable | After `LOGIN_MAX_FAILURES` (5) wrong passwords, sign-in is refused until this time (`LOGIN_LOCK_MINUTES`, 15). |
| `ask_account` | SMALLINT | 1 = expense entry asks which account paid (default). 0 = everything goes to the primary account. |
| `background_updated_at` | DATE, nullable | When the custom background picture last changed. `NULL` means the default background. |

**How it works**
- **Registration and approval:** registration creates a `PENDING` row, and every admin gets a notification.
  Login is refused until an admin sets the status to `APPROVED`. The first admin is created at startup from
  `ADMIN_USERNAME`/`ADMIN_PASSWORD`.
- **Reporting line (`manager_id`):** a manager can **view** the data of everyone below them, at any depth.
  If A manages B and B manages C, then B sees C, and A sees both B and C. If A has a manager M, then M sees A,
  B and C. Managers can only view their team's data, never change it. The admin cannot set a manager that
  would create a loop, and nobody can be an admin's manager.
- **Organisations (`org_admin_id`):** an `ORG_ADMIN` is the customer who bought the app for their
  organisation. On the Organisation page they add members (approved at once, with the org admin's plan), view
  their data read-only, lock, unlock and remove them (removal is backed up like an admin delete). Members are
  not told. Locking an org admin locks out every member until the org admin is unlocked. The `ADMIN` still
  sees and controls everyone.
- **Revoked access is silent:** removing a feature from a user's plan sends no notification (adding one does).
- **Username lock:** a user can change their own username only if `username_changed_at` is empty or more than
  `USERNAME_LOCK_DAYS` (15) days ago. Inside the lock they must raise a request (see
  `USERNAME_CHANGE_REQUESTS`). When an admin approves a request, `username_changed_at` is set to that moment,
  so the 15-day lock starts again.
- **Sign-in protection:** each wrong password raises `failed_logins`; at `LOGIN_MAX_FAILURES` the account is blocked
  for `LOGIN_LOCK_MINUTES` and the user gets a `SECURITY` notification. A password reset clears the block. On top of
  that, each IP address gets at most `LOGIN_IP_MAX_ATTEMPTS` sign-in attempts a minute (kept in memory, per process).

## PASSWORD_RESETS
Forgot-password requests. Each row is one email containing a temporary password and a one-time link.

| Column | Type | Meaning |
|---|---|---|
| `id` | INTEGER, PK | |
| `user_id` | INTEGER, FK → `app_users.id` | Whose password is being reset. Indexed. |
| `token_hash` | VARCHAR2(64), unique | SHA-256 of the secret in the emailed link. The link itself is never stored. |
| `temp_password_hash` | VARCHAR2(200) | bcrypt hash of the emailed temporary password. |
| `created_at` | DATE | When the reset was requested. Used for the 2-per-15-days limit. |
| `expires_at` | DATE | `created_at` + `RESET_TOKEN_MINUTES` (60). Set to "now" when superseded or disabled. |
| `used_at` | DATE, nullable | When the password was changed with it. A link works only once. |
| `failed_attempts` | INTEGER | Wrong temporary passwords entered. At 5 the link is disabled. |
| `requested_ip` | VARCHAR2(45) | IP that asked for the reset (IPv4 or IPv6), for auditing. |

**How it works**
1. *Forgot password?* on the login page asks for a username. The page always shows the same message, so it cannot
   be used to find out which usernames exist.
2. If the account exists and is approved, and it has had fewer than `RESET_MAX_PER_WINDOW` (2) resets in the last
   `RESET_WINDOW_DAYS` (15) days, a row is created and an email is sent with the temporary password and a link to
   `/reset-password?token=…`. Any older unused link for that user stops working. If the limit is reached, no
   row is created and the email explains when another reset is possible.
3. On the link page the user enters the temporary password and a new password. The new password is saved,
   `used_at` is set, and a `SECURITY` notification plus a confirmation email are sent.
4. Until then the old password keeps working. The temporary password **cannot** be used to sign in, only on the
   reset page.

Every request counts towards the limit, whether or not it was completed, so the reset email can't be used to spam
someone's inbox. Without SMTP settings, emails are saved as `.eml` files in `backend/mail_outbox/`.

## Split bills

```
SPLIT_GROUPS ──< SPLIT_MEMBERS >── APP_USERS (NULL for guests)
     │                 ▲
     ├──< SPLIT_BILLS ─┤ paid_by          created_by → APP_USERS
     │        └──< SPLIT_SHARES ─ member_id
     └──< SPLIT_SETTLEMENTS ─ from_member, to_member
```

Everyone in a group, app user or guest, is a `SPLIT_MEMBERS` row, and bills, shares and payments point at those
rows. Deleting a group deletes its members, bills, shares and payments (`ON DELETE CASCADE`). The links to
`APP_USERS` have no cascade on purpose: deleting a user would change other people's balances, so the admin
cannot delete a user who is or was in a split group, or created one, until those groups are deleted.

The first version stored participants by user id. On startup, `backend/app/migrate.py` moves such a database to
this layout: it recreates the bill, share and settlement tables (only if they are empty) and makes
`split_members.user_id` nullable.

| `description` | VARCHAR2(500), nullable | |
| `owner_id` | INTEGER, FK → `app_users.id` | Who created it. Always an admin of the group, cannot be removed, and is the only one who can delete it. |
| `created_at` | DATE | |

### SPLIT_MEMBERS

bills, payments and balance stay intact. The group page lists them as "left", and adding them again reactivates
the same row. The app keeps one row per user (or guest name) per group.

|---|---|---|
| `id` | INTEGER, PK | The member id used by bills, shares and payments. |
| `group_id` | INTEGER, FK → `split_groups.id` | |

| `guest_name` | VARCHAR2(100), nullable | The guest's name. `NULL` for app users. |

| `added_by` | INTEGER, FK → `app_users.id`, nullable | Who added them. Whoever added a guest can record that guest's payments. |
| `joined_at` | DATE | |
| `left_at` | DATE, nullable | Set when they were removed or left. |

### SPLIT_SHARES
One row per person on a bill.

| Column | Type | Meaning |
|---|---|---|
| `id` | INTEGER, PK | |
| `bill_id` | INTEGER, FK → `split_bills.id` | Unique together with `member_id`. |
| `member_id` | INTEGER, FK → `split_members.id` | |
| `share_type` | VARCHAR2(10) | `AMOUNT` (fixed amount), `PERCENT` (fixed percentage) or `EQUAL` (equal part of the rest). |
| `share_value` | NUMBER(14,4), nullable | The amount or percentage. `NULL` for `EQUAL`. |
| `amount` | NUMBER(12,2) | What they owe for the bill. Recalculated on every change. |

**How amounts are worked out** (`backend/app/services/splits.py`): fixed amounts and percentages come first,
and what is left is divided equally between the `EQUAL` shares. Amounts are rounded to paise so that they always
add up to exactly the bill total, and leftover paise go to whoever lost most to rounding. If nobody has an
equal share, the fixed shares must add up to the total.
- **Removing someone from a bill:** their amount is freed. If anyone left on the bill has an equal share, it
  goes into the equal part. Otherwise it is spread evenly over everyone left, by raising their fixed amount or
  percentage.
- **Adding someone to a bill:** they get an `EQUAL` share. Others keep their fixed amounts and percentages, so
  only the equal shares get smaller.

### SPLIT_SETTLEMENTS
Money paid back between two people.

| Column | Type | Meaning |
|---|---|---|
| `id` | INTEGER, PK | |
| `group_id` | INTEGER, FK → `split_groups.id` | |
| `from_member`, `to_member` | INTEGER, FK → `split_members.id` | `from_member` paid `to_member`. Whoever records it must be one of the two, or, for a guest, a group admin or whoever added the guest. |
| `amount` | NUMBER(12,2) | |
| `settled_on` | DATE | |
| `note` | VARCHAR2(500), nullable | |
| `created_by` | INTEGER, FK → `app_users.id` | Only this person can delete it. |
| `created_at` | DATE | |

**Balances:** for every pair of people, the shares one owes the other (as payer) minus the reverse, minus
payments between them. The group is settled when every pair is within one paisa.

### SUBSCRIPTION_CHARGES
One row per charge recorded on its due date. Unique on (`subscription_id`, `charge_date`), so a charge is never
recorded twice. `expense_id` points at the expense it was logged as (set to `NULL` if that expense is deleted).

**How it works:** the backend runs the subscription job every hour (at `SUBSCRIPTION_JOB_MINUTE`) and once on
startup. For each active subscription it records every charge whose date has arrived, moves `next_charge_date` on,
and sends the "renews soon" reminder. Adding or editing a subscription runs the same steps for that user at once.
Past charges before the subscription was added are not back-filled.

## Bank accounts and budgets

### ACCOUNTS
A bank account, card, wallet or cash that money is received in or spent from.

| Column | Type | Meaning |
|---|---|---|
| `id` | INTEGER, PK | |
| `user_id` | INTEGER, FK → `app_users.id` | Owner. Indexed. Names are unique per user. |
| `name` | VARCHAR2(60) | e.g. `HDFC Salary`. |

### ACCOUNT_TRANSFERS
Money moved between two of the user's own accounts (`from_account_id` → `to_account_id`, `amount`,
`transfer_date`, `note`). Not income and not spending, so it never changes the available balance or budgets.

### BUDGETS

notification and email; passing 100% sends another. Back-dated expenses in earlier months don't trigger alerts.

### USER_BACKGROUNDS
The custom background picture (`user_id` PK, `image` BLOB, `mime_type`, `updated_at`), kept out of `app_users` like
the avatar. Deleted by *Settings → Appearance → Reset to default*.

## JOB_RUNS
One row per run of a scheduled job (`job_name`, `run_key` unique, e.g. `daily_reminder` / `2026-10-30`, or
`subscriptions` / `2026-10-30T09`). With several worker processes each has its own scheduler; only the one that
inserts the row first runs the job. Rows older than 60 days are removed on startup.

## Accounting (double-entry books)

Each user with the Accounting feature has their own books. Everything in the reports is computed from
`VOUCHER_LINES`; expenses, funds and the rest reach the books only through vouchers.
The Tally group tree (Capital Account, Loans, Current Liabilities, Fixed Assets, Current Assets, Sales, Purchase,
Direct / Indirect Incomes and Expenses, Suspense, with their sub-groups) is fixed in `backend/app/accounting/chart.py`,
so ledgers store a `group_code` instead of pointing at a groups table.

### ACC_SETTINGS
One row per user; the books exist once it does.

| Column | Type | Meaning |
|---|---|---|
| `user_id` | INTEGER, FK, unique | Whose books. |
| `business_name`, `state`, `gstin` | VARCHAR2 | Shown on reports. `state` decides CGST + SGST or IGST on invoices. |
| `books_start` | DATE | 1 April of the first financial year (the year of the earliest transaction). |
| `lock_date` | DATE, nullable | Nothing dated on or before it may be posted, edited, deleted or reversed. |
| `locked_by`, `locked_at` | | Who set the lock and when. |
| `synced_at` | DATE | Last full re-sync with the user's transactions. |

### ACC_LEDGERS

| Column | Type | Meaning |
|---|---|---|
| `name` | VARCHAR2(100) | Unique per user. |
| `group_code` | VARCHAR2(30) | One of the fixed Tally groups. |
| `code` | VARCHAR2(30), nullable | Standard ledgers the app posts to (`CAPITAL`, `DRAWINGS`, `CASH`, `SUSPENSE`, `OUT_CGST`…). Unique per user, checked in code. |
| `opening_balance` | NUMBER(15,2) | Signed: debit positive, credit negative. Only balance-sheet ledgers have one. |
| `is_active`, `is_depreciation` | SMALLINT | Inactive ledgers can't be used in new manual vouchers. Depreciation ledgers are added back in the cash flow. |
| `account_id` | FK → `accounts`, unique, nullable | The bank account / card / wallet / cash this ledger stands for. |
| `split_group_id` | FK → `split_groups`, nullable | "Split – group": what the others in that group owe this user. |
| `gstin`, `state` | | For customers and suppliers. |

### VOUCHERS

| Column | Type | Meaning |
|---|---|---|
| `voucher_type` | VARCHAR2(10) | `PAYMENT`, `RECEIPT`, `CONTRA`, `JOURNAL`, `SALES`, `PURCHASE`. |
| `voucher_no`, `fy` | INTEGER | Numbered per type within the financial year (`fy` 2026 = 2026-27). Unique per user, type and year. |
| `voucher_date`, `narration` | | |
| `status` | VARCHAR2(10) | `POSTED`, or `REVERSED` once a reversal has been posted for it. |
| `is_reversal`, `reversal_of_id` | | A reversal mirrors the lines of the voucher it reverses, on the same date. Both stay in the books. |
| `source_type`, `source_id`, `source_version` | nullable | Auto-posted from an `EXPENSE`, `FUND`, `TRANSFER`, `SUB_CHARGE`, `SPLIT_BILL` or `SPLIT_SETTLEMENT`. Each change to the source reverses the old version and posts the next one. |
| `source_key` | VARCHAR2(80), unique, nullable | `EXPENSE:12:u3:v2`: makes posting the same version twice impossible (retries, concurrent requests). |
| `party_ledger_id`, `invoice_no`, `place_of_supply` | nullable | GST invoices. |

### VOUCHER_LINES
`voucher_id`, `ledger_id`, `line_no`, `debit`, `credit` (NUMBER(15,2); exactly one of them is non-zero) and, on the
sales / purchase line of a GST invoice, `gst_rate`. Every voucher's debits equal its credits.

### ACC_POSTING_RULES
Which ledger an expense category (`kind` = `EXPENSE_CATEGORY`) or a fund's source (`FUND_SOURCE`) posts to.
`rule_key` is the case-folded name, unique per user and kind. A missing rule is created on first use: a ledger of
the same name in an expense (income) group if there is one, otherwise **Drawings** (**Capital**), so personal
spending and personal money never change the business's profit. Changing a rule re-posts that category's
transactions in open periods.

### ACC_STOCK
Opening stock (first year only) and closing stock per financial year, entered by hand. Later years open with the
previous year's closing stock.

### BANK_IMPORTS / BANK_STATEMENT_LINES
An imported statement and its lines (`txn_date`, `description`, `reference`, `withdrawal`, `deposit`, `balance`).
`fingerprint` (unique per bank ledger) makes re-importing the same file a no-op. `matched_line_id` links a line to
the `VOUCHER_LINES` row it was reconciled with (`match_kind` `AUTO` or `MANUAL`); matches to reversed vouchers are
released automatically.

**How it works**
- **Auto-posting:** SQLAlchemy session hooks (`accounting/autopost.py`) note every expense, fund, transfer,
  subscription charge, split bill or settlement that is added, changed or deleted, and sync its voucher just before
  the commit. If that fails (for example a locked period), the whole change is rolled back.
- **Year end:** income and expense ledgers start each year at zero; earlier years' profit is carried into capital by
  calculation, so there is no closing entry to forget.
- **Deleting a user** (admin) backs up and deletes their books with the rest of their data.

## Imported records

The *Import Records* page brings past records in from a file. The records themselves are ordinary rows of
`EXPENSES`, `FUNDS` and `SPLIT_BILLS`; these two tables only keep the history of each upload.

### IMPORT_BATCHES
One row per upload (or per set of records typed in by hand).

| Column | Type | Meaning |
|---|---|---|
| `user_id` | INTEGER, FK | Whose records; each user imports into their own account. |
| `filename`, `file_type` | VARCHAR | As uploaded (`xlsx`, `csv`, `pdf`, `docx`…; `manual` when typed in). |
| `file_hash` | VARCHAR(64), nullable | SHA-256 of the file: warns when the same file is uploaded again. |
| `status` | VARCHAR(25) | `IN_PROGRESS`, `COMPLETED`, `COMPLETED_WITH_ERRORS`, `FAILED` (nothing imported), `UNDONE`, `PARTIALLY_UNDONE`. |
| `rows_total`, `rows_imported`, `rows_skipped`, `rows_failed`, `rows_undone` | INTEGER | Counts of the rows below. |
| `expense_total`, `income_total` | NUMERIC(14,2) | What was imported: spending (split rows at their full amount) and money received. |
| `created_at`, `finished_at`, `undone_at` | TIMESTAMP | |
| `created_accounts` | VARCHAR(500) | Ids (comma-separated) of the accounts the import created; a full Undo removes those nothing else uses (or deactivates one with entries in the books). |

### IMPORT_RECORDS
One row per row of the file.

| Column | Type | Meaning |
|---|---|---|
| `batch_id`, `user_id` | FK | |
| `row_no` | INTEGER | Row number in the file (1 = its first row). |
| `kind` | VARCHAR(10) | `EXPENSE`, `INCOME`, `SPLIT`, `TRANSFER` or `OPENING` (an account's opening balance). |
| `status` | VARCHAR(10) | `IMPORTED`, `SKIPPED` (a duplicate, a balance line or unticked), `FAILED`, `UNDONE`, `KEPT` (Undo left it: edited since, reconciled, or in a locked period). |
| `reason` | VARCHAR(500) | Why it was skipped, failed or kept. |
| `record_date`, `description`, `amount` | | As read from the file (after corrections in the review). |
| `fingerprint` | VARCHAR(64) | Kind, date, amount and description, plus which occurrence in the file: a row imported before is recognised when the file is uploaded again. Indexed with `user_id`. |
| `expense_id`, `fund_id`, `split_bill_id`, `transfer_id` | FK, SET NULL | What the row became (a split row: the expense for the user's share and the bill for the others; a transfer, or a category treated as one: an `ACCOUNT_TRANSFERS` row). |
| `account_id` | FK, SET NULL | An opening-balance row: the account whose `opening_balance` it added `amount` (signed) to; Undo takes it off again. |

### IMPORT_CHOICES
What a user chose in an import, filled in again the next time the same category or account name comes up (e.g. the
next year's file). One row per user, kind and value; unique on (`user_id`, `kind`, `source_key`).

| Column | Type | Meaning |
|---|---|---|
| `user_id` | FK, CASCADE | |
| `kind` | VARCHAR(10) | `CATEGORY` (a file's category → the app category), `TREATMENT` (a category → the account its rows were moved to) or `ACCOUNT` (a file's account name → an account). |
| `source_key` | VARCHAR(100) | The value from the file, normalised (case and spacing ignored). |
| `value` | VARCHAR(100) | The app category, or `id:<account id>`, `new:<KIND>:<name>` or `none`. |
| `updated_at` | TIMESTAMP | Last time the choice was made. |

## Who can see and change what

| Viewer → target | See | Change |
|---|---|---|
| Same user | ✔ | ✔ (expenses only within 3 days of creation) |
| Admin | ✔ everyone | ✔ everything, including locked expenses; can delete users |
| Manager, at any level above the target | ✔ | ✘ |
| Viewer in `DATA_SHARES` | ✔ | ✘ |
| Anyone else | ✘ | ✘ |

These rules are enforced in `backend/app/deps.py` (`access_level`, `resolve_target`) on every API call,
not only in the UI.
